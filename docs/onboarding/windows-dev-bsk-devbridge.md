# คำสั่งสำหรับ Claude: ตั้งค่า bsk บน Windows, เรียนรู้ Dev Bridge, แปลง Saved Search เป็น SuiteQL

ไฟล์นี้เขียนถึง Claude ที่ทำงานบนเครื่อง Windows ของ dev (ผู้ใช้คือคนที่ส่งไฟล์นี้ให้คุณ) ให้อ่านทั้งไฟล์ก่อน แล้วทำตามทีละขั้น
ตอบผู้ใช้เป็นไทยคำอังกฤษคำ สั้น ตรงประเด็น หยุดรอผู้ใช้ทุกจุดที่เขียนว่า "รอผู้ใช้"

## ข้อเท็จจริงที่รู้แล้ว (อย่าถามซ้ำ)

- Windows + Chrome (ที่ login NetSuite อยู่แล้ว)
- role ของผู้ใช้เป็น Administrator และ Dev Bridge deploy ไว้ในบัญชีแล้ว
- ผู้ใช้มีแค่บัญชี production (ยังไม่มี sandbox) ดังนั้นทุกอย่างที่ทำต้อง "อ่านอย่างเดียว"
- ใช้ skill ใน plugin `bombot-forge`: `setup-browser`, `browser-engines`, `ns-live-verify` อ่านก่อนลงมือ
  ถ้ายังไม่มี plugin นี้ ให้หยุดแล้วบอกผู้ใช้ ห้ามติดตั้งเองโดยไม่ถาม

## กฎที่ห้ามพลาด

- ห้ามเขียน/แก้/ลบข้อมูลใน NetSuite ทุกกรณี ห้ามคลิกปุ่ม submit/save/delete ใดๆ
- ห้ามเดา id/URL/เวอร์ชัน/ชื่อ field/ชื่อ table ถ้าไม่แน่ใจให้ตรวจจากระบบจริงหรือถามผู้ใช้
- `bsk` กด accept dialog ให้เองปิดไม่ได้ ดังนั้นหลัง navigate ทุกครั้งต้องติด dialog guard และตรวจ identity gate
  (company/environment ตรงกับที่ผู้ใช้บอก) ตามสูตรใน skill `browser-engines` ก่อนอ่านต่อ
- ก่อนใช้ `bsk` ครั้งแรกของงาน แจ้งผู้ใช้ 1 บรรทัด: ทำอะไร, บัญชี/หน้าไหน, เป็น Agent Window เบื้องหลังที่ปิดเมื่อเสร็จ
- ห้ามอ่านหรือพิมพ์ password เด็ดขาด ห้าม kill daemon ที่รันอยู่ และห้าม `bsk session stop --all`
  (ปิดได้เฉพาะ session id ของตัวเอง)
- ติดตั้งอะไรก็ตามต้องอ่านสคริปต์ให้ผู้ใช้ดูและรอผู้ใช้ OK ก่อน การคลิกติด extension ใน Chrome เป็นของผู้ใช้ Claude ทำแทนไม่ได้

## ขั้น 1: ตรวจสถานะ (อ่านอย่างเดียว ทำได้เลย)

- มี `bsk` หรือยัง: `Get-Command bsk -ErrorAction SilentlyContinue` ; `$env:BSK_AUTO_START='0'; bsk status --json`
- มี `~/.config/bombot-forge/browser.json` อยู่แล้วหรือไม่ (ถ้ามี = รอบ update ไม่ใช่เครื่องใหม่ อ่านก่อนแล้วอย่าทับ)
- มี python ใช้ได้ไหม: ลอง `python --version` และ `py --version` (skill ใช้ `python3` ซึ่งบน Windows อาจเรียกไม่ได้ ให้รายงานว่าใช้คำสั่งไหนได้)
- สรุปให้ผู้ใช้ 2-3 บรรทัดว่าอะไรมีแล้ว อะไรขาด แล้วรอผู้ใช้

## ขั้น 2: ติดตั้ง bsk

- บน Windows ให้ทำตาม `AGENT_INSTALL.md` ของ upstream (Tencent/BrowserSkill) อ่านให้ผู้ใช้ดูก่อนว่ามันทำอะไร ห้ามด้นวิธีเอง
  รอผู้ใช้ OK แล้วค่อยรัน
- เปิดหน้า extension ให้ผู้ใช้ (ลิงก์อยู่ใน skill `setup-browser` ขั้น 2a) แล้วบอกว่า "Add to Chrome แล้วเปิดการเชื่อมต่อใน popup" ผู้ใช้กดเอง
- `bsk install-skill --harness claude-code`
- ตรวจ: `$env:BSK_AUTO_START='0'; bsk status --json` ต้องเห็น browser ที่ connected

## ขั้น 3: ให้ daemon เปิดตอน Log on แบบไม่มีหน้าต่าง (สำคัญบน Windows เพราะ `bsk` เริ่ม daemon เองไม่ได้)

- อ่าน `skills/setup-browser/references/windows-daemon-hidden.md` ใน plugin แล้วทำตาม runbook ในนั้น
- เป็นการแก้ค่าถาวรของเครื่อง (Task Scheduler + ไฟล์ .vbs) ให้สรุปแผนแล้วรอผู้ใช้ตอบ OK ก่อนลงมือ
- ถ้ามี daemon เก่ารันอยู่ ห้าม kill เอง ถามผู้ใช้ก่อน
- ใน reference เขียนไว้ว่าสูตรนี้ "สังเกตจากเครื่องเดียว ยังไม่ครบ" ให้ทำตามนั้นและรายงานผลจริงตอนจบ

## ขั้น 4: ทดสอบ Dev Bridge (ping)

- ขอให้ผู้ใช้ก๊อปปี้ URL หน้า Home ของบัญชีที่ใช้งานมาวาง แล้วสร้าง `<ACCOUNT>` จาก URL นั้น (อย่าเดา)
- ใช้ script id/deploy id เริ่มต้นตาม skill ถ้า ping ไม่ผ่านให้ถามผู้ใช้หา id จริงจาก script record
- รัน ping ผ่าน `ns-live-verify` (ตัวช่วย `ns_read.py` ใช้ `bsk` เป็น engine) ตรวจว่า `account`, `envType` ตรงกับที่ผู้ใช้คาด
  และ `user.isAdmin` เป็น true
- บอกผู้ใช้ชัดๆ ว่ากำลังอ่านบัญชีไหน (เป็น production)
- ถ้าเจอหน้า login ให้ถามผู้ใช้ว่าอนุญาตให้คลิกปุ่ม Login ให้ไหม (ตามขั้น 5 ของ skill `setup-browser`,
  Chrome ต้อง autofill ให้เองและห้ามอ่านช่อง password) ถ้าไม่ผ่านให้ผู้ใช้กดเอง

## ขั้น 5: สอน action ทีละตัว (ครบทุก action)

ทุกข้อรันตัวอย่างอ่านอย่างเดียว อธิบาย 2-3 บรรทัด แล้วรอผู้ใช้บอกว่า "ต่อ"

1. `ping` และ `help`: ดู account/user/serverTime และรายการ action
2. `query`: SELECT เท่านั้น (ห้าม WITH, ห้าม `;`) ตัวอย่างปลอดภัย: `SELECT COUNT(*) AS n FROM account` สอน gotchas จาก skill:
   `acctnumber` เป็น string, `LIKE` ต้องใส่ quote, checkbox ได้ `'T'`/`'F'`, multiselect ได้ null (ต้องใช้ `record` แทน),
   `ORDER BY DESC` บนตารางใหญ่ต้องจำกัดช่วง, ตอบเป็น HTML "Notice" = session หมดอายุ, คืนได้สูงสุด 1000 แถว
3. `record`: โหลด record เป็น JSON แบบเลือก field (ให้ผู้ใช้เลือก record ที่จะดู) และแบบ `meta` ที่เห็น field/sublist id
4. `lookup`: อ่าน field ของ record เดียวแบบเร็ว
5. `feature`: เช็ก feature เปิด/ปิด (ดูชื่อที่ใช้ได้จาก `help` หรือ README ของ Dev Bridge อย่าเดาชื่อ)
6. `search`: แบบ ad-hoc (type + filters + columns) และแบบ saved search ด้วย `--search-id`
   หมายเหตุ: skill เขียนไว้ว่า saved search (`--search-id`), `--meta` และ `--filters-json` ที่มี filter จริง
   "ยังไม่เคยทดสอบบนระบบจริง" ให้ลองกับ saved search ที่ผู้ใช้เลือก แล้วรายงานตามจริงว่าผ่านหรือไม่
   ถ้าผลต่างจากที่ skill บอก ให้บอกผู้ใช้ ห้ามแก้ skill เอง

ปิดท้ายด้วยโจทย์ฝึก 2 ข้อ: ให้ผู้ใช้เขียน SuiteQL เองแล้วคุณตรวจให้ ก่อนรัน อธิบายให้ฟังว่าแต่ละส่วนผิดหรือถูกเพราะอะไร

## ขั้น 6: จบการตั้งค่า

- ปิด session `bsk` ของตัวเอง แล้วเช็กว่า id นั้นหายจาก `bsk session list` (อย่าคาดว่าจำนวนต้องเป็น 0)
- บันทึก prefs ตามขั้น 6 ของ skill `setup-browser` (ไม่มี secret) และ id ที่ไม่ใช่ค่าเริ่มต้นเท่านั้น
- ห้ามใส่ account id จริงลงไฟล์ที่ commit ใน repo ใดๆ

## ขั้น 7: บทเรียนเข้มข้น แปลง Saved Search เป็น SuiteQL ให้ผลตรง 100% และใช้งานได้ 100%

เป้าหมาย: ผลของ SuiteQL ตรงกับ saved search เดิม และทุก table/column id มาจากการตรวจจริง ไม่ใช่การเดา
ให้ผู้ใช้เลือก saved search เล็กๆ 1 ตัวเป็นโจทย์ฝึก ทำตามนี้ทีละข้อ อธิบายเหตุผลของแต่ละข้อให้ฟัง และรอผู้ใช้ทุกข้อ

หลักคิด: ไม่เชื่อ "ดูแล้วน่าจะถูก" ต้องมีหลักฐาน 4 ชั้นที่พิสูจน์คนละแบบ (ข้อ 2, 4, 5, 6) เพราะแต่ละชั้นพลาดคนละเรื่อง

### 7.1 เอา definition จากของจริงบนบัญชีตอนนี้

- ห้ามเชื่อไฟล์ XML หรือคอมเมนต์ในโค้ดโดยไม่เทียบกับของจริง (เคยเจอ search จริงมี `ROUND` แต่ XML และคอมเมนต์ในโค้ดเก่าไม่มี
  ทำให้เทียบผิดและได้ผลต่างหลอก) ถ้าสองแหล่งขัดกัน ให้ถือของ live
- อ่านจาก `search.load()` ทั้ง `filterExpression` และ columns ห้ามดูแค่ `filters[]`
  เพราะ array ไม่บอกโครง AND/OR ถ้ามี OR แล้วเขียน SQL เป็น AND ล้วนจะผิด แต่ผลอาจบังเอิญตรงบนข้อมูลชุดหนึ่ง
- วิธีอ่าน: Dev Bridge `search` ด้วย `--search-id` (ยังไม่เคยทดสอบ ให้ลองแล้วรายงาน) หรือ `object:import` ของ savedsearch
  แบบอ่านอย่างเดียว ถ้า XML ใน repo ต่างจากของจริง ให้บอกผู้ใช้ก่อนทำต่อ

### 7.2 ทำตาราง semantic map ทีละ clause

- ตารางมีคอลัมน์: ลำดับ, filter/column, field id ของ search, join, operator, ค่า, formula, summary type, แปลเป็น SQL ว่าอะไร,
  และสถานะ "แปลตรงตัว" หรือ "ตีความ"
- clause ที่เป็น "ตีความ" ต้องหาหลักฐานเพิ่มก่อนเชื่อ
- column ช่วยบอกเจตนาของ search ได้ดีที่สุด (ชื่อ label บอกว่า search ถามหาอะไร)
- ตัวอย่างการแปลที่เคยยืนยันแล้ว: `noneof @NONE@` = `IS NOT NULL`, `DECODE(a,b,1,0)=1` ⟺ `a = b`
- แปลง formula ตรงตัว ห้ามย่อหรือเปลี่ยนความหมาย ตรวจก่อนว่า SuiteQL รองรับฟังก์ชันนั้น
  (ที่เคยใช้จริงมี `NVL`, `ROUND`) และระวังการปัดเศษ: field แบบ currency เก็บทศนิยมจำกัด
  เทียบกับผลคูณที่ไม่ปัดจะได้ผลต่างหลอกเสมอ ให้ปัดทั้งสองฝั่งให้ตรงกับที่ search ทำ

### 7.3 ตรวจ table/column id ทีละตัว (ห้ามเดา)

- SuiteQL ไม่มี INFORMATION_SCHEMA ให้ใช้ Records Catalog ของ NetSuite: GET แบบ same-origin ที่
  `/app/recordscatalog/rcendpoint.nl?action=getRecordTypeDetail&data={"scriptId":"<record type>"}`
  (key คือ `scriptId` ไม่ใช่ `id`) ได้ `fields[]` และ `joins[]` ของ record type นั้น
  หมายเหตุ: โน้ตของโปรเจกต์ที่เคยใช้บอกว่าใช้ได้ แต่ยังไม่ได้ยืนยันบนเครื่องนี้ ให้ลองแล้วรายงาน
- ผลก้อนนี้ใหญ่และมี URL ปนอยู่ ให้ parse บนหน้าเว็บแล้วคืนเฉพาะ id ที่ต้องใช้ ห้ามคืน JSON ดิบ
  (ตัวกลางของ browser บางตัวบล็อกข้อความที่มี URL)
- ใช้ `record` แบบ `meta` (ขั้น 5 ข้อ 3) เป็นอีกทางเทียบ field id
- ทุก column ที่จะใช้ต้องถูกพิสูจน์อีกชั้นด้วย SELECT จริงผ่าน Dev Bridge (จำกัดแถวตามวิธีใน skill `ns-live-verify`)
  error แบบ invalid identifier = ชื่อผิด ห้ามแก้ด้วยการเดาชื่อใกล้เคียง
- field id ของ search กับของ SuiteQL ไม่จำเป็นต้องเหมือนกัน (ตัวอย่างที่ยืนยันแล้ว: table `account` ใช้ `name`/`displayname` ไม่ได้
  ต้องใช้ `fullname`) field แบบ custom (custrecord_/custcol_) มักใช้ id เดียวกัน แต่ต้องตรวจทุกตัว
- ทำตารางผลตรวจ: ชื่อใน search -> table.column ใน SuiteQL -> ตรวจแล้ว (แหล่งไหน/query ไหน/ผลอะไร) หรือ "ยังไม่ตรวจ"

### 7.4 Funnel test: พิสูจน์ว่า join ไม่พังเงียบและไม่ทำให้แถวเพิ่ม

- รัน `COUNT(*)` ทีละ filter แบบสะสม ดูว่าจำนวนแถวลดลงตามที่คาดในแต่ละขั้น
  "0 แถว" อาจแปลว่า join ผิด ไม่ใช่ว่าไม่มีข้อมูล funnel แยกสองอย่างนี้ออกจากกัน
- ถ้า join ทำให้แถวเพิ่มเป็นหลายเท่า ให้ดูว่า filter ตัวไหนยุบกลับมาเท่าต้นทาง
  (เทียบ `COUNT(*)` กับ `COUNT(DISTINCT key)` ต้องเท่ากันตอนจบ)
- search ผูก join ให้โดยอัตโนมัติ แต่ SQL ต้องเลือก INNER/LEFT เอง ตรวจให้ตรงกับพฤติกรรมของ search

### 7.5 Sandwich run: เทียบผลบนบัญชีจริงแบบอ่านอย่างเดียว

- ยิงเรียงเป็น OLD -> NEW -> OLD (OLD = saved search เดิม, NEW = SuiteQL ใหม่)
- ถ้า OLD รอบแรก == OLD รอบสอง แปลว่าข้อมูลนิ่งในช่วงนั้น ผลต่างเชื่อได้ ถ้าไม่เท่ากัน ให้ทิ้งรอบนั้นแล้วรันใหม่ ห้ามสรุปว่าต่าง
- เกณฑ์รับ: NEW ขาด = FAIL เสมอ, NEW เกิน = รับได้ก็ต่อเมื่ออธิบายสาเหตุได้
- เทียบให้ครอบคลุมสิ่งที่ผู้เรียกใช้จริง: ถ้าโค้ดอ่านจาก search แค่ id เดียว เทียบชุด id (missing/extra) ก็พอ
  แต่ถ้าใช้ค่าหลายคอลัมน์ ต้องเทียบค่าทุกคอลัมน์ตาม key ด้วย (อธิบายผลต่างระดับทศนิยมถ้ามี)
- รายงานจำนวนแถวของทั้งสองฝั่งทุกครั้ง

### 7.6 Edge probe: ยิงทุกครั้ง

- ฟิลด์ที่ชี้ record ที่ถูกลบ (referential integrity) มีกี่แถว
- transaction ที่ไม่มี mainline row มีกี่แถว
- ค่าที่เกาะขอบการปัดเศษ: มีแถวที่ `0 < |diff| < 0.01` หรือไม่ ถ้ามี การปัดที่ต่างกันระหว่าง search engine กับ SuiteQL อาจทำให้ผลพลิก
  ถ้าไม่มี ปิดเรื่อง precision ได้

### 7.7 เกณฑ์ผ่าน

ต้องผ่านครบทุกข้อถึงจะบอกว่า "เสร็จ":

1. id ทุกตัวตรวจแล้วจากระบบจริง
2. semantic map ครบทุก clause และข้อที่ "ตีความ" มีหลักฐาน
3. funnel test ผ่านและ join ไม่ fan-out
4. sandwich run: OLD รอบแรก == OLD รอบสอง, missing 0, extra 0 (หรืออธิบายส่วนเกินได้), ค่าต่าง 0
5. edge probe ครบ

ถ้าข้อใดไม่ผ่านให้แก้ตามหลักฐาน ห้ามเดา และถ้า search ใช้ความสามารถที่ SuiteQL ทำตรงๆ ไม่ได้ ให้บอกผู้ใช้ตรงๆ ว่าแปลงไม่ได้เพราะอะไร

### 7.8 เขียนโค้ดใช้งานจริง (SuiteScript 2.1)

- ใช้ `query.runSuiteQLPaged` (pageSize 1000) วนทุกหน้า ถ้าต้องใช้ `IN` กับ id จำนวนมากให้แบ่งก้อนละไม่เกิน 900
- ถ้า join ใดมีหน้าที่แค่ "กรอง" (ไม่ได้ดึง column มาใช้) ให้ลองแยกเป็น query ที่สองบน id ที่ได้จาก query แรก
  และถ้าเร็วขึ้นต้องวัดจริงก่อนเชื่อ
- ถ้า script นี้จะรันแทน search เดิมแบบ scheduled ให้เสนอ canary: ให้ของเก่าเป็นค่าเริ่มต้นเดินคู่กับของใหม่ก่อนสลับ
  แล้วถามผู้ใช้ก่อนตัดสินใจ
- บอก governance ของ script type ที่จะใช้ โดยดูตารางใน skill `teibto-codereview` (ห้ามจำเอง)
- เก็บ definition ของ search ต้นฉบับเป็นคอมเมนต์เลขกำกับไว้ในโค้ด (พร้อมวันที่ที่เทียบกับของ live)

### 7.9 กับดักตอนวัดเวลาและตอนรัน

- วัดเวลาด้วย full fetch ใน server script เท่านั้น การนับด้วย `runPaged` ฝั่ง browser ได้เลขต่ำกว่าความจริง
- เวลาของ search เดียวกันแกว่งตามโหลดของบัญชี ให้วัดหลายรอบ และอย่ายิง query อื่นคู่ขนานตอนวัด
- ระหว่างที่ search หนักรันอยู่ renderer อาจไม่ตอบ ให้ poll ซ้ำก่อนสรุปว่าค้าง
