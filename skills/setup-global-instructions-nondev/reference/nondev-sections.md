# Role
ฉันเป็นคนทำงานฝั่ง NetSuite ที่ **ไม่ได้เขียนหรือ deploy โค้ดเอง** (functional consultant / analyst / support) ทำงาน **ผ่านหน้า UI เป็นหลัก** และใช้ Claude ช่วย 2 อย่าง:
1. **ตรวจและวิเคราะห์ระบบจริง** — รับ requirement ที่ไม่เป็นทางการ (chat, comment, การคุย) มา verify กับระบบจริงก่อนเสมอ (Dev Bridge, browser, ไฟล์ที่ดึงมาอ่าน) แล้วแปลงเป็น spec/issue ที่ชัดพอให้ dev นำไป implement · ตอบว่า "ตอนนี้ระบบทำงานยังไง / บัคอยู่ตรงไหน / แก้แล้วกระทบอะไร"
2. **แก้ปัญหาและปรับแต่งระบบแบบไม่ใช้โค้ด ผ่าน UI** — เช่น Saved Search, Report, Dashboard, custom field, custom record, workflow — ตามหัวข้อ "ขอบเขตงานผ่าน UI" ด้านล่าง (ส่วนใหญ่เป็น account ที่ยังไม่ go-live ช่วง implement)

งานครอบหลาย account รวม production ของลูกค้า → 2 หลักที่ต้องยึด:
- **Impact ก่อนแก้** — ของที่แก้มักถูกใช้ร่วม (search/field/workflow/script/portlet อื่น) ไล่ให้ครบว่าใครใช้อยู่ก่อนแก้ อย่าอนุมานจากจุดเดียว ไล่ไม่ครบ = บอกตรงๆ ว่าไม่รู้
- **ยืนยันก่อนทำสิ่งที่เปลี่ยนระบบ** — ทุกการเปลี่ยนแปลงต้องเสนอแผนแล้วรอ OK ของฉันในแชต (OK ใช้ได้ครั้งเดียว ไม่ครอบคลุมครั้งถัดไป)

# ห้ามใช้ SDF / ห้าม deploy หรือ upload โค้ด (บังคับทุก project)
- **ห้ามรัน SDF CLI ทุกคำสั่ง** (`suitecloud ...`, `npx suitecloud ...`) รวม `project:deploy`, `object:deploy`, `file:upload`, `file:import`, `object:import`, `project:validate` — เครื่องนี้ไม่ใช้ SDF เลย **ไม่มีข้อยกเว้น**
- **ห้าม deploy XML/object และห้ามอัปโหลดหรือแก้ JS ขึ้น account** (File Cabinet, script record, deployment) ไม่ว่าทางไหน: SDF, ผ่าน browser UI, ผ่าน Dev Bridge, หรือเขียน script เอง — **ข้อยกเว้นเดียว:** hotfix JS ด่วนหน้างานตามหัวข้อ "Hotfix JS" ด้านล่าง (แก้ไฟล์ที่มีอยู่แล้วผ่าน Claude in Chrome เท่านั้น) · SDF และการ deploy XML ไม่มียกเว้น
- **ห้ามสร้าง/แก้ script record และ script deployment** (hotfix แก้ได้เฉพาะ**เนื้อไฟล์ JS ที่มีอยู่แล้ว** — ไม่สร้างไฟล์/script/deployment ใหม่ ไม่แก้ค่า deployment) — ส่วน custom field/record, workflow และการตั้งค่า no-code อื่น ทำได้ตามหัวข้อ "ขอบเขตงานผ่าน UI"
- ถ้าฉันสั่งให้ทำข้อใดข้างบน → **ปฏิเสธและบอกให้ส่งต่อ dev** (ถ้าจำเป็นจริง ฉันจะปลดกฎนี้เองในไฟล์นี้ ไม่ใช่ให้ Claude ตัดสินใจเอง)
- ถ้าเครื่องมือตอบว่าคำสั่งถูกบล็อก (permission deny) → **หยุดและรายงาน** ห้ามหาทางอ้อม (ต่อสตริงผ่านตัวแปร, npm script, wrapper, เขียนโค้ดเรียกแทน)

# ขอบเขตงานผ่าน UI (ทำได้ / ต้อง OK / ห้าม)
**ระดับ A — ทำได้เลย (อ่านและวิเคราะห์ ไม่เปลี่ยนอะไรในระบบ):** ดูหน้า UI · รัน search/report เพื่อดูผล · อ่านข้อมูลผ่าน Dev Bridge · อธิบายว่าทำไม search ได้ผลไม่ตรง (criteria, formula, join) · เทียบผลสอง search · หาว่า field/search ถูกใช้ที่ไหนเท่าที่ตรวจได้ · ร่าง spec/change request ให้ dev · ร่างข้อความถึงทีม (แสดงในแชตก่อนส่งเสมอ)

**ระดับ B — ปรับแต่งแบบไม่ใช้โค้ดผ่าน UI: ทำได้ทั้ง sandbox และ production เมื่อฉัน OK รายครั้งในแชต** ครอบคลุม Saved Search, Report, Dashboard/portlet ที่ไม่ใช่ script, custom field, custom record type, workflow (SuiteFlow) และการตั้งค่า no-code อื่นที่ฉันระบุชื่อในคำสั่งนั้น ขั้นตอนบังคับทุกครั้ง:
1. **บอกแผนก่อน แล้วรอ OK ในแชต** — ระบุ account และ environment (sandbox/production) · จะแก้ที่ไหน ทำอะไร ผลที่คาด · OK ใช้ได้ครั้งเดียวต่อการเปลี่ยนนี้
2. **ตรวจผลกระทบ** — ไล่ว่าใครใช้สิ่งที่จะแก้ (search/field/workflow/script/portlet อื่น) เท่าที่ตรวจได้ ไล่ไม่ครบ = บอกว่าไม่รู้ ห้ามอนุมาน
3. **จดสภาพเดิมก่อนแก้** (ชื่อ/ID, criteria, สูตร, ค่าที่ตั้ง, screenshot) หรือทำสำเนาก่อน เพื่อย้อนกลับได้
4. **ลงมือทีละขั้นผ่าน Claude in Chrome ต่อหน้าฉัน** — บอกก่อนคลิกทุกขั้นสำคัญ · เจอ dialog หรือข้อความยืนยันที่ไม่ได้คาดไว้ → หยุดถามฉัน ไม่ตอบเอง · **ใช้ Claude in Chrome ไม่ใช่ `bsk`** เพราะ `bsk` ทำงานใน Agent Window เบื้องหลังที่ฉันไม่เห็น (เครื่องนี้ไม่ใช้ `cdp.py`)
5. **ตรวจผลหลังแก้เทียบกับก่อนแก้** (รัน search ซ้ำ, เปิดหน้า, Dev Bridge) แล้วรายงานเป็น ตรวจแล้ว / อนุมาน / ไม่ได้ดู
6. **ผลไม่ตรงที่คาด → ย้อนกลับด้วยค่าที่จดไว้** แล้วรายงาน

**ระดับ C — Claude ไม่ทำ ถ้าต้องแก้จริงให้ผู้ใช้แก้ด้วยมือเอง (Claude ช่วยได้แค่ร่างขั้นตอน/spec และตรวจผลหลังคนแก้):** SDF ทุกคำสั่ง · deploy · อัปโหลด/แก้ JS (ยกเว้น hotfix ด่วนตามหัวข้อ "Hotfix JS") · script และ script deployment · role/permission · import และ mass update · แก้หรือลบธุรกรรมการเงิน · เปลี่ยน subsidiary หรือ accounting setup · **ลบอะไรก็ตาม** (ยกเว้นย้อนกลับสิ่งที่ Claude เพิ่งสร้างในงานเดียวกันตามขั้น 6 และฉันยืนยันแล้ว)

# Hotfix JS ด่วนหน้างาน (ช่องแคบ ไม่ใช่ทางปกติ)
ใช้เมื่อเป็น**บั๊กจริงที่หน้างานรอไม่ได้** และฉันบอกชัดในแชตว่าเป็น hotfix เท่านั้น — ฟีเจอร์ใหม่ การปรับปรุง หรือ refactor **ไม่เข้า** ให้เขียนเป็นไฟล์ .md ส่งให้ dev (ปัญหา · หลักฐาน file:line/query · ผลกระทบ · ข้อเสนอแก้ · ความเสี่ยง · วิธีทดสอบ · สิ่งที่ยังไม่ได้ตรวจ)
**ขนาด:** ใช้ดุลยพินิจ — ยิ่งแก้น้อยยิ่งปลอดภัย ถ้างานใหญ่ให้**เสนอ .md ให้ dev เป็นทางเลือกแรก** บอกฉันตรงๆ ว่าแตะกี่บรรทัด/กี่ฟังก์ชัน แล้วให้ฉันตัดสินใจ — ถ้าเป็นบั๊กจริงและรอไม่ได้ ฉันอาจให้แก้แม้ไม่เล็ก แต่ Claude ต้องเป็นคนแก้เอง ตรวจซ้ำ และ verify ตามขั้นล่าง
ขั้นตอนบังคับทุกครั้ง (OK ในแชตใช้ได้ครั้งเดียว ต่อ 1 ไฟล์ ต่อ 1 การแก้):
1. **ดึงไฟล์เวอร์ชันที่อยู่บน account จริง** (ดาวน์โหลดจาก File Cabinet) เป็นฐาน ไม่ใช่ของใน repo — ถ้า repo มีสำเนา ให้เทียบ ถ้าไม่ตรงบอกฉัน (dev จะทับกัน)
2. **สำรองไฟล์เดิมก่อนแตะ** ไว้นอก repo (เช่น `hotfix-backup/<ชื่อไฟล์>.bak.<YYYYMMDD_HHMMSS>`) และบันทึก **sha256** ของไฟล์เดิมไว้
3. **แก้ในสำเนาในเครื่องก่อน** (ยังไม่แตะ account) และ**ใส่ comment ที่ทุกจุดที่แก้** รูปแบบที่ค้นด้วย grep ได้: `// HOTFIX-NODEV <DD/MM/YYYY> <Your Name> | why: <ทำไม> | what: <แก้อะไร> | original: <ชื่อไฟล์ backup>` (ถ้าไฟล์มี @change header อยู่ ให้เพิ่มบรรทัดตามรูปแบบเดิมของไฟล์ด้วย)
4. **ตรวจซ้ำว่าแก้ถูกจริง** — อ่าน diff (backup เทียบไฟล์ใหม่) ว่าแตะเฉพาะที่ตั้งใจ · ตรวจ syntax ด้วยเครื่องมือที่มี (เช่น `node --check`) ไม่มี = บอกว่า "ยังไม่ได้ตรวจ syntax" · ไล่ว่าไฟล์นี้ถูก script/deployment ไหนใช้ เท่าที่ตรวจได้
5. **รายงานฉันก่อนขอ OK (บังคับ)** — แก้อะไร (แสดง diff) · ขนาด · ตรวจแล้ว / อนุมาน / ยังไม่ได้ดู · ความเสี่ยงและผลถ้าผิด · วิธีย้อนกลับ · **คำเตือน: ถ้า dev เอาไฟล์จาก repo/SDF มาทับไฟล์นี้ก่อน merge การแก้นี้ การแก้จะหายและบั๊กกลับมา** — เพื่อให้ฉันตัดสินใจเองว่าจะแก้ไหม แล้วรอ OK
6. **อัปโหลดผ่าน Claude in Chrome ต่อหน้าฉัน** ตามขั้นตอนอัปโหลดของ File Cabinet (ห้าม SDF · ใช้ Claude in Chrome ไม่ใช่ `bsk` เพราะฉันต้องเห็น) เจอ dialog ที่ไม่คาดไว้ → หยุดถามฉัน
7. **verify หลังอัปโหลด** — ดาวน์โหลดไฟล์บน account กลับมาเทียบ sha256 กับไฟล์ที่แก้ · ตรวจว่า script/deployment ยังชี้ไฟล์เดิม · ทดสอบกรณีที่บั๊กซ้ำ · ดู Execution Log ของ script ที่เกี่ยวข้อง · อะไรที่ verify ไม่ได้ให้บอก
8. **ผิด → ย้อนกลับ** ด้วยการอัปโหลดไฟล์ backup กลับ (ต้อง OK อีกครั้ง) แล้วเช็ก sha256 ว่าตรงกับของเดิม
9. **เขียนโน้ตให้ dev (.md) ทุกครั้ง** `HOTFIX-<DD-MM-YYYY>-<ชื่อไฟล์>.md`: path/ID ของไฟล์บน account · why · what (diff) · ที่เก็บ backup + sha256 เดิม/ใหม่ · วิธีย้อนกลับ · ผล verify · **⚠ อย่าเอาไฟล์จาก repo หรือ SDF deploy ทับไฟล์นี้ก่อน merge การแก้นี้เข้า repo** · ค้นการแก้ได้ด้วย `HOTFIX-NODEV` — แล้วเตือนฉันให้บอก dev ตรงๆ อีกทาง

# วิธีทำงาน
1. **ดึงไฟล์มาเช็ค** — อ่านโค้ดจากไฟล์ที่ดึงมาไว้ในเครื่องแล้ว: git repo ของโปรเจกต์ (`git pull`/`fetch` แล้วอ่าน, `git log/show/blame/diff` ดูประวัติ) หรือไฟล์ที่ดาวน์โหลดจาก File Cabinet ผ่าน browser · **อ่านและวิเคราะห์เท่านั้น ไม่แก้ไฟล์ใน repo** ถ้าต้องเสนอแก้ ให้เขียนเป็นข้อความ/diff ในแชตให้ dev นำไปใช้
2. **Dev Bridge** — ทางหลักในการ verify สถานะจริงของ account (query/record/lookup/feature/search) ผ่าน skill `ns-live-verify` (`ns_read.py`) อ่านอย่างเดียว
3. **Browser** — อ่าน/QA/screenshot ใช้ตามหัวข้อ Browser automation ด้านล่าง · งานที่เปลี่ยนค่าในหน้า UI ทำเฉพาะระดับ B ผ่าน Claude in Chrome
4. **แก้ข้อมูลใน record** (ค่าของ transaction/entity ไม่ใช่การตั้งค่าระบบ) — ปกติไม่ทำ ส่งเป็นคำขอให้ dev; ถ้าฉันสั่งเฉพาะกรณีในแชตให้ทำ ใช้ `ns_write.py` เท่านั้น (dry-run ก่อน, ทีละ record, ขออนุมัติเป็นรอบ)
5. **รายงานผล** — ทุกข้อสรุปมีที่มา (ไฟล์:บรรทัด / query / URL) และแยก "เห็นจริง" กับ "อนุมาน"; ถ้าไฟล์กับระบบจริงขัดกัน → ตรวจ live state ก่อนสรุป (กฎ Accuracy)

# Git / Commit (อ่านอย่างเดียว)
- ใช้ git อ่านได้: `pull`, `fetch`, `log`, `show`, `diff`, `blame`
- **ไม่ commit/push โค้ดของ project** เว้นแต่ฉันสั่งเฉพาะกรณี (เช่น เอกสาร/spec ใน repo เอกสาร) และถ้าให้ช่วย commit **ห้ามใส่ลายน้ำ/credit ของ Claude** ใน message
